# ESP32 电机远程测试系统：项目需求与开发交接

> **当前状态：硬件已经买回来了，准备在本机开始测试和开发。**
>
> 这份文档用于交接给开发人员或本机开发 Agent，避免反复解释项目背景。重点是我要实现的功能、现在可以开始做的事情，以及哪些能力仍需要现场验证。
>
> **请从现有硬件的识别、基础示例验证和本地原型开发开始，不要重新从选购开发板、AI 聊天机器人或完整工业平台设计讲起。**

## 1. 我到底要做什么

我要做一个用于**电机研发与测试现场的无线音视频及仪器通信盒子**。

目前的工作方式是：人员坐在电机或测试设备旁边，通过数据线连接设备，收集数据、分析、调整参数，再重新测试。有些测试环境不适合人员长期停留。

希望改成：

- 开发板留在测试设备附近，通过短线连接仪器或电机控制器。
- 开发板通过 Wi-Fi 与我的电脑通信，我不必一直坐在设备旁边。
- 在电脑上查看仪器数据和波形、现场画面，并听到和记录电机声音。
- 在电脑上发送调参命令，经开发板转交给对应设备，再观察实际变化。
- 后续可能同时连接三至四台 USB 设备，并逐步增加其他接口设备。

**核心定位：开发板主要是一个双向无线通信中介，同时负责现场摄像头和麦克风采集；主要显示、存储、分析和业务逻辑放在电脑上。**

不是要用 ESP32 重新制造示波器，也不是要把电机的高速控制算法搬到电脑和 Wi-Fi 上。

## 3. 系统职责与连接关系

### 3.1 建议架构

```text
                         测试现场

电机控制器  ←── 对应有线接口 ───────────┐
示波器      ←── USB / LAN 等接口 ───────┤
其他仪器    ←── 对应有线接口 ───────────┼── ESP32 开发板
                                      │       ⇅
摄像头      ── 套件配套接口 ───────────┤     Wi-Fi
麦克风      ── 板载音频采集电路 ───────┘       ⇅
                                           我的电脑
                                显示、监听、记录、分析、参数操作
```

这是目标结构，具体接口以真实设备为准。不能根据示意图就推断某台仪器已有可用驱动。

### 3.2 板端负责什么

板端优先保持轻量：初始化硬件、采集音视频、建立设备连接、转发数据与命令、必要的缓存、连接状态报告和断线处理。

板端可以不理解波形的物理含义，但必须实现实际接口所需的主机功能、握手、帧处理或驱动。**“只做中介”不等于可以省略接口协议。**

### 3.3 电脑端负责什么

电脑端负责设备列表、视频显示、声音监听、音频与波形保存、仪器命令生成、数据解析、实时曲线、参数操作、测试记录及后续分析。

能放在电脑端完成的仪器语义解析和分析逻辑，优先不要塞进板端。

### 3.4 两种调参必须区分

| 操作 | 命令应发给谁 | 观察什么 |
|---|---|---|
| 修改电机运行或控制参数 | 电机控制器，或实际掌握这些参数的设备 | 仪器测量、控制器状态、声音和画面的变化 |
| 修改示波器量程、时基、触发等 | 示波器 | 示波器配置与波形显示的变化 |

不能把“从示波器读取波形”和“通过示波器修改电机参数”混为一谈。具体电机参数接口由后续控制程序提供，现阶段不要猜寄存器、命令字或允许值。

## 4. 第一阶段必须做出来的功能

### 4.1 开发板能正常开发和独立运行

先确认本机能够识别开发板，使用对应板型和芯片版本的工程完成编译、烧录、日志查看和重启验证。

先跑厂家或芯片原厂的匹配示例，再逐步修改。不要一开始同时更换框架版本、重写驱动并整合全部功能，否则难以定位问题。

需要记录能够复现的工具链、依赖版本和配置。不要仅因某个版本“最新”，就替换厂家示例所需版本。

### 4.2 摄像头：电脑能实时看到画面

目标是将真实摄像头画面通过无线网络传到电脑，而不是仅保存在板端或只在本地屏幕显示。

第一版先保证画面连续、链路可观察、断线可识别。分辨率、帧率、编码和延迟依据实际硬件与示例确定，做成可配置项，不预先承诺高清、低延迟和多任务同时满速。

优先使用套餐摄像头及配套接口。没有确认现有配件不可用前，不追加采购 USB 摄像头。

### 4.3 麦克风：电脑能听、能录

目标是获取真实现场声音，并在电脑端实时监听、录音和回放。麦克风优先使用板载收音硬件，不把独立声卡或外置麦克风作为第一版前置条件。

**这是电机噪声采集，不是语音助手。**用于分析的音频应尽量保留原始信号：

- 不默认开启语音降噪、自动增益、语音活动检测或静音裁剪。
- 使用可记录的固定采集增益；确实存在无法关闭的处理时，要明确标注。
- 保留实际采样率、位宽、声道数、增益、时间信息及丢帧情况。
- 录制尽量保存为适合分析的原始 PCM 或 WAV；监听传输是否压缩可独立设计。

第一版可以做声音波形、频谱和相同采集设置下的相对比较。**没有声学校准前，不把数字录音幅度包装成准确声压级或 dB(A) 检测结果。**

摄像头、麦克风先分别验证，再验证两者同时工作。喇叭播放不是本阶段的核心需求，不应让板子播放声音干扰电机收音。

### 4.4 双向通信：不仅上传数据，还能返回命令

电脑应能向指定设备发送命令，板子应能转交并返回响应。没有真实仪器时，先使用模拟设备验证整个交互过程。

需要区分“命令已发送”“设备已接收”“参数已生效”“被拒绝”“结果未知”。网络请求成功不能直接显示为设备修改成功。

不同设备应有独立标识，避免把设备 A 的命令发给设备 B，或把不同设备的数据混在同一条曲线上。

### 4.5 电脑端的最小界面

先做一个轻量页面或本机应用，不做复杂管理平台。至少能够查看：

| 区域 | 第一版内容 |
|---|---|
| 连接状态 | 开发板、网络、采集状态、最后更新时间、异常信息 |
| 视频 | 真实摄像头画面 |
| 音频 | 开始/停止监听和录音、录音文件、基础波形；频谱可逐步增加 |
| 仪器数据 | 模拟曲线起步，后续替换为真实仪器数据；清楚标记来源 |
| 命令操作 | 选择目标设备、提交测试命令、显示执行状态 |
| 测试记录 | 同一次测试关联参数变化、测量数据、录音和必要截图 |

本地原型默认在局域网运行，数据保存在本机或明确配置的本地存储，不以云账号、大模型服务或公网部署为前提。

## 5. 三至四个 USB 设备：必须提前保留的能力

### 5.1 扩展目标

```text
USB 设备 1 ──┐
USB 设备 2 ──┤
USB 设备 3 ──┼── 独立供电的 USB Hub ── 开发板 USB Host 接口
USB 设备 4 ──┘
```

最后讨论的 NANO 方案是通过 USB Host 接口外接 Hub，而不是要求主板直接带四个 USB 插口。具体端口用途必须依据实物确认，不能把烧录用接口当成主机口。

套件摄像头和板载麦克风应尽量继续使用各自专用连接，不占外接仪器的 USB 插口。

### 5.2 需要验证的层次

**物理接口够用、USB 设备能枚举、驱动能访问、仪器数据正确、多设备同时稳定，是五个不同层次。**

推进顺序：

1. 确认 USB Host 基础功能，使用手头可获得的一台已知设备验证。
2. 识别 Hub，记录型号、供电方式、USB 速率和拓扑。
3. 枚举多个设备，记录 VID/PID、序列号、设备类和连接位置等信息。
4. 逐一接入所需设备类驱动和仪器协议。
5. 验证多设备并发，再加入摄像头和麦克风负载。

如果手头没有四台真实设备，必须把结论限定在实际测试范围内。四个模拟对象不能证明四台实体 USB 仪器已经稳定接入。

### 5.3 不应提前作出的承诺

- 不承诺所有 USB 仪器插上就能用。
- 不承诺四个端口拥有四份独立上行带宽。
- 不默认高速 Hub 与不同速率设备在当前框架版本下全部兼容；核对实际使用版本的主机栈限制。
- 不把 ESP32 数据转发自动等同于通用 USB-over-IP，也不默认电脑上的厂家驱动可以不加适配地通过无线链路访问仪器。
- 不假定 Hub 能安全地反向给主板供电；按主板和 Hub 各自要求供电，核实电源与接法。

USB 类别可能涉及虚拟串口、USBTMC 或厂家专用协议。具体采用什么方案，要根据设备识别结果和说明书决定，而不是根据插头外形决定。

## 6. 没有现场仪器，怎么先开发和验证

### 6.1 三类数据必须明确区分

| 数据类别 | 说明 | 能证明什么 |
|---|---|---|
| 真实音视频 | 开发板摄像头和麦克风实际采集 | 音视频采集与传输链路 |
| 模拟仪器数据 | 程序生成波形、状态及命令响应 | 界面、协议设计、日志和业务流程 |
| 真实仪器数据 | 实际示波器或其他设备返回 | 对应型号及当前配置下的接入效果 |

界面和日志均应记录来源。不能因为页面有曲线，就宣称已经连接示波器。

### 6.2 模拟器应该实现什么

模拟设备至少提供身份查询、状态读取、波形获取、参数写入及执行结果，并能模拟掉线、延迟、拒绝命令和数据中断。

例如改变一个模拟参数后，模拟波形发生可预期变化，用于验证“命令—响应—显示—记录”的闭环。**这只是通信与软件验证，不是实际电机模型或物理性能验证。**

先允许电脑端或板端软件模拟，降低启动门槛。后续具备接线条件时，再让通信真正经过开发板的有线设备侧与无线电脑侧。

应明确区分两种结果：

```text
软件模拟闭环通过：证明程序流程可用。
实际经过板子有线端/无线端的转发通过：证明被测通信路径可用。
```

两者都不能替代真实仪器的驱动验证。

### 6.3 在家可开展的测试

可以用说话声、键盘声或普通风扇声验证收音和录制；摄像头拍摄室内画面即可。不要为了原型验证临时搭建未经确认的电机功率实验。

当前没有真实仪器不应阻碍音视频、电脑端、网络、模拟器和数据记录功能开发。

## 7. 接真实仪器时的原则

### 7.1 示波器不是必然主动推送

设备可能主动发送，也可能需要电脑先发命令查询，再返回测量结果或波形。系统要支持双向请求与响应，而不是只写一个被动接收器。

具体示波器型号、接口、编程手册、数据格式和吞吐能力都待确认。不要根据“有 USB/网口”就猜测具体命令。

### 7.2 优先利用仪器已有能力

现有示波器负责采样、触发和必要的波形缓存。开发板负责接入和传输，不重新做高带宽模拟采集前端。

如果仪器本身支持方便的网络访问，可以使用对应网络路径，不必强行让所有设备都走 USB。也不要求所有仪器采用同一个驱动。

### 7.3 实时性分别测量

采样率、数据读取频率、网络传输延迟、界面刷新率、调参生效时间不是同一个指标。

第一版先保证数据正确、连续且状态可观察，再根据测试调整刷新率和吞吐。高速事件可以采用仪器本地采样、缓存与批量回传；不能用无线链路承担电机 PWM 或高速闭环控制。

多仪器同时采集也不自动意味着精确同步。需要严格对齐时，另行确认设备时间戳、触发或时钟同步方案；网关接收时间不得伪装成精确采样时间。

## 8. 数据、命令与可靠性要求

### 8.1 最小可追溯信息

测量记录至少关联设备标识、数据来源、序号、时间、量值或波形格式、单位和采样配置。设备无法提供采样时间时，明确使用“网关接收时间”或“电脑接收时间”。

操作记录至少关联请求编号、目标设备、参数名、原值、目标值、时间和结果。关联同一次测试的音频、视频或截图、波形和操作日志。

### 8.2 命令可靠性

需要具备超时、有效期和重复请求处理。超时后不要直接认定失败或盲目重发；优先确认设备状态。断网重连后不得自动重放过期写命令。

真实设备默认只读。每次只开放经过确认的参数，明确数据类型、单位、允许范围和允许运行状态。控制权限应避免多个操作端互相覆盖。

### 8.3 负载与断线

音视频和仪器数据并行时，不能让视频持续占满缓存、阻塞命令或悄悄丢失重要测量记录。采用合理的限速、缓冲和分流策略，并报告实际丢帧、积压或中断。

实时预览与原始数据归档可以采取不同策略：预览优先新鲜度，记录优先完整性；做不到完整保存时，必须标记缺口。

电脑端界面断开时，板端应有明确行为。是否继续录制、缓存多久、重连如何处理，应在实现中说明，不能无限堆积数据。

## 9. 安全边界与暂不做的内容

### 9.1 实际设备接入边界

开发板接的是仪器或控制器允许的通信接口。**不要把电机相线、高压信号或不明电平直接连接到开发板 GPIO。**涉及隔离、接地、接口电平和功率系统的连接，必须由现场具备相应经验的人员确认。

电机原有控制与保护留在现场。远程网页按钮、普通 Wi-Fi 命令和后续 AI 都不能替代急停、过流、超速等保护。

失联后保持、减速、停机或其他策略要结合真实系统确认，不预设“任何情况立刻断电”都安全。重启或重连不能自行启动电机。

开发板属于原型平台。没有测试依据前，不宣称它可以直接承受现场极端温度、湿度、振动或强干扰。能放在试验环境外的设备优先放在外面。

### 9.2 当前不作为前置条件的事情

- 小智 AI、语音助手、机器人功能和大模型自动调参。
- 自研 PCB、焊接全部电路或一次性补齐所有工业接口。
- 替代示波器的高速模拟采样功能。
- 正式声级计认证、工业整机认证或安全认证。
- 触摸屏 UI、PoE、复杂云平台、微服务和公网远程访问。

需要时后续再做，不应阻挡本地音视频及通信原型。

## 10. 建议实施顺序与验收

| 阶段 | 工作内容 | 必须留下的验证证据 |
|---|---|---|
| A. 识别和建环境 | 确认实物、端口、芯片版本；匹配示例和工具链；编译、烧录、日志验证 | 硬件记录、环境版本、构建与启动日志、可复现步骤 |
| B. 分别跑通功能 | 网络连接、摄像头、麦克风分别测试 | 真实画面、真实录音、网络访问结果、实际配置 |
| C. 联合音视频 | 网络预览和监听，电脑端录音；观察并行负载 | 连续运行记录、帧率/音频配置、异常和资源占用 |
| D. 双向模拟闭环 | 电脑命令经板端服务处理，模拟设备响应并改变波形 | 请求、响应、曲线和日志对应；显著标识模拟来源 |
| E. USB 和 Hub | 单设备枚举、Hub、多设备枚举与适配，逐步增加负载 | 实际 Hub、设备清单、速率/拓扑、已通过与未通过项目 |
| F. 现场真实接入 | 先读一台真实仪器，再接控制器；确认安全条件后开放一个参数 | 型号及协议记录、真实数据核对、写入确认、异常行为 |

A、B、C、D 是当前可以优先推进的工作。E 根据手头 Hub 和设备条件完成到可验证的层次。F 在真实设备可用时开展。

首轮联测可以暂以连续运行 30 分钟作为工程检查目标，再按实测延长；**这只是建议测试口径，不是已达成的性能结论或工业稳定性承诺。**

每个阶段必须区分“尚未开发”“已编译”“已烧录”“单项实测通过”“联合实测通过”。不要把编译成功写成硬件验证成功。

## 11. 软件组织与交付要求

### 11.1 软件方向

板端优先沿用实际板型对应的 ESP-IDF/BSP 与示例。电脑端可以使用 Python 和轻量 Web 界面，优先利用现有软件开发经验。传输协议按负载选择，不为追求某个技术名词重写已可用链路。

视频、音频、仪器连接和控制命令要有清晰模块边界。多个厂家示例最终需要整合进同一应用工程，不能将“依次刷入多个独立固件”当作功能叠加。

可以采用如下目录结构，也可以用等效组织方式：

```text
project/
  firmware/       # 板端应用、板型配置和硬件适配
  pc_backend/     # 电脑端通信、仪器适配、存储与分析
  pc_ui/          # 监控和操作界面
  simulators/     # 模拟仪器与故障模拟
  docs/           # 接线、运行、协议、验证记录
  data/           # 本地测试数据，默认不提交仓库
```

Wi-Fi 密码、设备凭据和实际测试数据不得直接提交到公开仓库。提供无敏感信息的配置模板。

### 11.2 需要交付什么

交付内容应至少包含：

1. 实际硬件与配件清单、板卡/芯片版本、端口用途和接线说明。
2. 可重复构建的板端工程、电脑端程序和无敏感信息的配置示例。
3. 本机安装、编译、烧录、启动、查看日志和恢复步骤。
4. 示例固件与正式整合固件之间的关系，以及已测试的版本组合。
5. 音视频、USB、模拟设备和真实仪器的测试记录，明确各自验证范围。
6. 当前限制、已知问题和下一步计划，优先列影响现场接入的阻塞项。

演示时要说明：现在看到的哪些是真实采集，哪些是模拟；哪些接口已经验证，哪些只是预留。

## 12. 交给开发 Agent 的执行要求

请直接基于现有硬件推进，不要重复展开购物建议或要求我再次描述需求。

开始时先检查本机环境和实际连接的板子，整理缺失的关键事实。能自动确认的不要反复询问；需要人工看实物或接线的，提供准确的一次性检查项。

随后优先跑通最小板端工程和厂家匹配示例，并行准备电脑端界面及模拟器。先逐项验证音视频、网络和 USB，再进行整合，不要一次性改动所有层。

没有仪器型号时，不猜协议，不宣称已经支持所有示波器。没有真实设备时继续开发可验证部分，不把现场条件作为全项目停工理由。

进行可能影响原有固件、配置或用户文件的操作前，说明影响并准备可行的备份或恢复方式。不要为了让示例运行就直接擦除全部存储、修改不可逆配置或覆盖无关项目。

汇报以实际结果为准：本次做了什么、真实测试得到什么、还缺什么、下一步做什么。不要只列技术选项而不执行，也不要在缺乏证据时将计划写成已完成。
