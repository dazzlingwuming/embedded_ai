# 网关与音频协议 v1

## 控制台视频预览

当前现场运行 0.6.0 联合固件，摄像头、麦克风、喇叭和网关同时可用。
控制台也保留对历史摄像头独立固件的识别；只有恢复该旧程序时才禁用它没有提供的音频／仪器功能。
摄像头与 ES8311 共用 GPIO7/8 的 I2C 总线，避免重复创建互相冲突的总线实例。

GET `/api/camera/status` 提供可用状态、分辨率、JPEG 画质、真实接收帧率、帧数、最近帧大小及连接错误。
还包含最近 60 秒的 `interval_p95_ms`、`max_interval_ms`、`low_1pct_fps`；
最慢 1% 帧率为最慢一组帧间隔均值的倒数，至少 100 个间隔后提供，不能当作平均 FPS。
WebSocket `/ws/camera` 先返回 JSON 来源信息，然后每个二进制消息为一张完整原始 JPEG。
多个浏览器共享一条板端 MJPEG 连接，每个浏览器只排队保留最新一帧；断开最后一个浏览器后释放上游。
断线返回错误并结束预览，不能把旧帧当作持续的视频。切换页面或隐藏浏览器时暂停读取。
画面只在本机局域网中转，不送入 AI 服务。

POST `/api/camera/capture` 把新鲜帧保存到 `data/camera-photos/` 并返回同源查看链接。
超过三秒没有新帧时拒绝保存；GET `/api/camera/photos/<文件名>` 仅允许生成的 JPG 文件名。
POST `/api/camera/config` 接收 `{"quality":40}`，允许 20～90 的整数，仅修改 JPEG 压缩质量。
它调用板端配置接口并重新读取确认，不修改传感器分辨率或宣称固定帧率。

## 连接与来源

当前 P4 固件 `firmware/` 开启真实摄像头、麦克风、喇叭和网络模拟器 RPC；
控制 HTTP 80，原始采集 HTTP 81，播放 WebSocket 82，MJPEG HTTP 83，AEC 语音 HTTP 84。
板端 `/api/get_camera_info` 返回视频端口与路径，电脑读取该信息，不把端口 81 固定认作视频。
相机连续采集以维持曝光调整，预览编码上限 20fps，输出 800×800；无订阅者时不持续编码 JPEG。
JPEG 缓存只保存最新图像，不累积待播帧；锁只用于复制，不覆盖网络发送过程。
电脑服务只监听 `127.0.0.1:8765`。板端接口为受信局域网原型，没有配置公网认证。
`source=real_microphone` 与 `source=simulated` 分别标记真实收音和虚拟仪器数据。
`board_id` 是 P4 的 eFuse 基础 MAC，`boot_id` 是每次启动生成的随机标识。

## 板端 API（端口 80）

| 请求 | 用途 |
|---|---|
| GET `/api/status` | 固件、启动标识、堆内存、采集配置、丢帧、四个设备槽状态 |
| GET `/api/get_camera_info` | 传感器状态、分辨率、JPEG 画质与视频 URL |
| POST `/api/set_camera_config` | 调整 JPEG 画质；控制台限制为 20～90 的整数 |
| GET `/api/capture_image` | 获取当前新鲜 JPEG |
| POST `/api/sim/register` | 注册 device_id、session_id、name、source=simulated |
| GET `/api/sim/poll?device_id=...&session_id=...` | 心跳和领取最早的排队命令 |
| POST `/api/sim/result` | 返回 device_id、session_id、request_id、source、state、result |
| POST `/api/commands` | 新建命令或返回相同 ID 的已有结果 |
| GET `/api/commands/<request_id>` | 查询状态、结果和是否为迟到确认 |

命令 JSON 示例（只适用于虚拟仪器）：

```json
{
  "request_id": "unique-id-per-user-action",
  "device_id": "sim-01",
  "method": "set_parameter",
  "params": {"name": "amplitude", "value": 2},
  "ttl_ms": 3000
}
```

方法：identify、read_status、read_waveform、set_parameter、set_fault。
TTL 为网关接收后的有效时长，允许 200～30000 ms；设备每约 300 ms 轮询，6 秒无心跳显示离线。
命令返回 gateway_boot_id，便于检查响应确实来自本次板端运行。

| 状态 | 含义 |
|---|---|
| queued | 网关已收，设备尚未领取 |
| received | 设备已领取，尚未确认执行结果 |
| completed | 查询完成 |
| applied | 模拟参数已执行 |
| rejected | 参数、设备或请求被拒绝 |
| expired | 领取之前过期，不再派发 |
| unknown | 已领取但没有结果，或电脑无法确认网关响应；可能已执行 |

设备会话变化时，旧 queued 变为 expired，旧 received 变为 unknown。
同一缓存内 request_id、载荷一致时返回原结果，不再次派发；载荷变化返回 409。
板端保留最近 16 个命令槽，模拟器去重缓存 128 个结果，均为内存缓存，重启清空。
**这是有界去重，不是永久 exactly-once 承诺**；不要跨重启或缓存淘汰后手动重放旧修改请求。
电脑端不会自动重试写入。提交响应丢失后只 GET 查询原 request_id，
确认等待最多延长至 TTL 加六秒，网关执行 TTL 不变。结果未知时先读取状态核对，
再决定是否建立新的用户操作。
迟到结果可将 unknown 更新为最终状态并标记 late_result，原始状态变化保留在日志。

故障模拟：normal、reject、timeout（不返回结果）、lost_ack（写入生效但丢确认）、
offline（约八秒断线）。set_fault 本身仍可响应，以便恢复 normal。

## 真实音频（端口 81）

GET `/audio` 返回 `application/octet-stream`，HTTP chunked。仅供一个电脑采集连接使用，
电脑再分发给浏览器并保存 WAV。HTTP chunk 边界不作为音频帧边界。

每个包为 24 字节小端头加 960 个 int16 PCM，Python struct 格式 `<4sIQIHH`：

| 字段 | 类型 | 含义 |
|---|---|---|
| magic | 4 bytes | ASCII BLA1 |
| sequence | uint32 | 自板端启动递增的帧序号 |
| capture_us | uint64 | 板端单调时间估算的采集起始时刻 |
| sample_rate | uint32 | 48000 |
| samples | uint16 | 960，每帧 20 ms |
| flags | uint16 | bit0 表示本帧存在接近满量程的采样 |
| pcm | int16[960] | 单声道、未经电脑端处理 |

板端采集队列在 PSRAM 中保存 256 帧（约 5.12 秒、486 KiB），满时丢最旧帧。
stream_drops 记录当前流的丢弃数；
没有订阅者时的正常覆盖独立计为 idle_overwrites。read_errors 表示实际采集读取错误。
开始一次新流时队列清空，只提供当时之后的声音。

电脑用序号检测缺帧，录音内补等长静音、写入 gaps；超过五秒的序号跳变或音频连接中断
将结束文件并标记 interrupted。音频 socket 最长等待八秒，实际断开立即结束文件；
TCP 连接内的短时等待可以使用板端缓存恢复。浏览器显示队列与 WAV 写入独立，
界面丢帧不等于录音缺帧。
原始录音期间板端功放关闭；电脑预览默认静音。可视频谱是基础 DFT 展示，不是校准声压测量。

## 板上扬声器（0.4.0 起，端口 82）

WebSocket `/speaker`，同一时间一个播放所有者。音频固定为 48000 Hz、16 bit、小端单声道，
板上复制到两个 I²S 时隙。连接先返回 hello，包含 sample_rate=48000。

发送 `{"type":"begin","volume":75}` 开始新轮，音量允许 0～100（0.5.1 起），默认 75。
板子先作废旧轮并清空队列，返回 begun，提供 epoch、consumed=0、window=16。
二进制帧为 16 字节头加 PCM，struct `<4sIIHH`：

| 字段 | 类型 | 含义 |
|---|---|---|
| magic | 4 bytes | ASCII BLP1 |
| epoch | uint32 | begun 返回的播放轮编号 |
| sequence | uint32 | 每轮从 0 连续递增 |
| samples | uint16 | 1～960，末帧允许不足 20 ms |
| flags | uint16 | 必须为 0 |
| pcm | int16[samples] | 48000 Hz 单声道 |

板端 PSRAM 队列 32 帧，电脑按窗口 16 帧限流；每消费四帧通知 consumed。
发送 `{"type":"end","epoch":当前编号}` 后，等待 drained，包含 DMA 尾部排空和功放关闭。
重复序号不重复播放；取消轮的旧音频和旧 end 不影响新轮。
格式错误、乱序、溢出、I²S 错误会取消播放；超过三秒无后续帧会超时关闭功放。

WebSocket `{"type":"cancel"}` 或端口 80 的 POST `/api/speaker/cancel`（请求体 `{}`）
都会立即关闭功放、更新 epoch、清空队列；WebSocket 关闭也会取消。
电脑同时使用有序 WS 取消和独立 HTTP 取消，避免等待音频积压；没有自动补播。
新轮启用功放之前留出 DMA 排空时间。TCP 音频与播放确认启用 TCP_NODELAY。

## 电脑 API 与文件

POST `/api/recordings/start`、`/stop`，GET `/api/recordings`；
GET `/api/recordings/<session>/<audio.wav|metadata.json|events.jsonl>`。
POST `/api/simulators/start`（count=1～4）、`/stop`。
POST `/api/commands`、GET `/api/commands/<id>`；POST `/api/config` 更新局域网板子地址。
WebSocket `/ws/audio` 向浏览器发送相同音频包。

WAV 元数据记录采样设置、板端配置快照、起止时间、样本数、缺帧和削顶统计。
events.jsonl 关联同次录音里的命令；全局审计见 `data/commands.jsonl`。
这些时间未与真实仪器同步，不能直接当作跨仪器的精密同步证据。

## 本机实时语音 API

| 方法与地址 | 用途 |
|---|---|
| GET `/api/voice/status` | 脱敏配置、会话状态、收发统计、最近转录 |
| POST `/api/voice/config` | 保存 API Host、ASR/TTS 模型、音色、音量等；可带 api_key，不回显 |
| POST `/api/voice/start` | 启动云 ASR → DeepSeek → 云 TTS 会话 |
| POST `/api/voice/self-test` | 真实板子加回环协议测试端；无需 API |
| POST `/api/voice/interrupt` | 作废旧回答、清空队列、取消生成并停止板上播报 |
| POST `/api/voice/stop` | 结束连接并停止播放 |
| POST `/api/console/stop` | 优雅关闭本机服务，包括关闭语音链路 |

控制台只监听 127.0.0.1:8765。原始录音和语音会话互斥，避免将播放声混入测量录音。
真实通话固定使用 `fun-asr-realtime` 识别、现有 DeepSeek 生成文字、`cosyvoice-v3-flash` 合成，
不走直接语音问答模型。只把最终识别句送入 DeepSeek；部分转写用于界面显示和提前确认插话，不能启动新回答。
按句流式合成回复；旧会话或被打断轮次的迟到音频丢弃。测试回环端点只用于无 API 协议自检。
语音上行副本为 16 kHz PCM，云端下行为 24 kHz PCM，播放转为 48 kHz；原始录音路径不重采样。
语音会话默认上限 600 秒，可设 0 为不限时；到时完成当前回答再结束，手动结束立即生效。
长回复不使用隐藏的 30 秒音频或整轮 90 秒截断；网络错误结束通话，无自动重连或补播。
默认自动打断模式持续上传板上 AEC 输出，由 WebRTC VAD 与云 ASR 文字共同确认插话；
插话时先停止板上声音，再取消 DeepSeek/TTS，保留同一 ASR 流和插话开头。
可选的轮流说话模式仍在播报期间上传静音心跳；语音处理副本与原始 WAV 分开。
关闭网页不会自动结束后台会话，请主动调用 stop。配置与测试说明见 `实时语音接入与自检.md`。

## 本机 Wi-Fi 版本组合

当前锁定 ESP-IDF 5.5.4、esp_wifi_remote 0.14.5、ESP-Hosted 1.4.6，与
[厂家 ESP-IDF 5.x 示例版本路线](https://github.com/waveshareteam/ESP32-P4-Platform/blob/6f78fa810ec505048c1941e3d09cefc9f29129bd/docs/P4_C6_HOSTED_WIFI.md)
一致。SDIO 40 MHz、四位总线，复位 GPIO54，管脚见 sdkconfig.defaults。
RPC 小响应启用 TCP_NODELAY，传输层统计写入串口健康日志。
联合固件额外锁定 esp_video 2.6.0。SSID、RSSI、信道与 IPv4 缓存在板端，约十秒更新，
状态查询不会每次额外发起 C6 Wi-Fi RPC。当前实际 SSID 为 `现场Wi-Fi（名称已脱敏）`。
模拟器 HTTP 重试保留设备会话，已执行命令的结果确认可以幂等重传；
这些操作不重新执行设备命令，故障模式 lost_ack 则刻意不重传确认以验证 unknown 语义。

此前尝试 3.1.0 时，原厂 C6 未报告新驱动需要的 SDIO aggregate 上界，接收缓冲
冻结到 1536 字节后拒绝 2048 字节读取，导致网络停止推进。曾保留动态缓冲进行兼容修补，
修复这个阻塞后并发负载仍出现间歇超时。该尝试归档于 `.cache/esp-hosted-3.1-patched/`，
不再作为当前组件覆盖；失败证据保留在日志。
最终恢复厂家匹配的 1.4.x 路线，精确版本由依赖锁定文件固定。
没有改写 C6 固件或 eFuse；不能从旧固件缺少版本字段反推出精确出厂版本。


## AEC/VAD 语音流（0.6.0，端口 84）

GET `/speech` 返回 BLV1 包，32 字节小端头格式 `<4sIQIHHHHHH`：
magic、sequence、capture_us、sample_rate=16000、samples=320、flags、mic_rms、reference_rms、clean_rms、speech_ms。
后随 320 个 int16 的 AEC 输出，每包 20ms。flags bit0=VAD 语音、bit1=功放启用、bit2=AEC 启用、bit3=处理输入缺口。
输入缺口会结束语音会话，不把参考错位的声音用于自动打断。

诊断 GET `/speech?debug=1` 使用 BLD1 头，并依次附 clean、mic、reference 三个 320-sample 数组，整包 1952 字节。
仅用于项目内声学检查；正常 ASR 上传只包含 clean PCM，不发送诊断原麦克风和 DAC 参考数组。

ES8311 使用 ADCL+DACR 同步参考（寄存器 0x44=0x58），48kHz 双通道经官方采样率转换到 16kHz，
交给 ESP-SR `AEC_MODE_FD_LOW_COST` 和经典 WebRTC VAD。原始采集 81 端口仍只提供 ADC 左声道的 48kHz 音频。
算法只在语音流有订阅者时处理。I2C 仍与摄像头共用 GPIO7/8，不增加识别、合成或唤醒模型分区。

DSP 依赖只保留 P4 所需库与头文件，版本、许可、逐文件官方 SHA-256 在
`firmware/components/esp-sr/UPSTREAM.json` 和 `firmware/components/esp_audio_effects/UPSTREAM.json`。
使用 `scripts/prepare-speech-dsp.py` 可通过 Direct 直连重现，不下载整套离线语音模型。

真实喇叭单端声学证据见 `data/duplex-acoustic-check.json`，不能仅凭 ready 标志判断回声效果。
用户随后已明确确认自动插话能够停下旧回答并回答新问题，见 `data/manual-duplex-user-feedback.json`。
